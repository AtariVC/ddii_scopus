# Конвенции построения виджетов


## 1. Разметка в `.ui`, логика + стиль в `.py`

`.ui` нужен только крупным сборным виджетам (сейчас `connection_bar`, `file_tree`
в `widgets/composite/`). Простые контролы и индикаторы — чистый Python
(`paintEvent`/QSS) без `.ui`.

**Структура composite: каждый виджет — в своей папке-пакете.** Все виджеты из
`widgets/composite/` лежат в собственной папке с именем виджета:
`widgets/composite/<name>/` содержит `<name>.py`, `<name>.ui` (если есть) и
`__init__.py`, который реэкспортит класс(ы) (`from .<name> import <Class>`). Это
держит пару `.py`+`.ui` вместе и одинаково для всех composite. Публичный импорт не
меняется: `composite/__init__.py` делает `from .<name> import <Class>` (резолвится в
папку-пакет). Контролы и индикаторы остаются одиночными `.py` — папку заводим
только для composite.

**В `.ui` (front) — только структура и статика:** layout'ы, вложенность,
margins/spacing, `sizePolicy`, `objectName`, статические тексты/`placeholderText`,
**пустые layout-слоты** под рантайм-виджеты, и промоушен кастомных виджетов через
`<customwidget>`.

**В `.ui` НЕ должно быть:** логики/обработчиков; хардкод-цветов/шрифтов в
`styleSheet`; фиксированной геометрии окна вместо layout'ов.

**В `.py` (back):** аннотации виджетов из `.ui` на уровне класса (имя аннотации =
`objectName`, для типов и автодополнения); создание рантайм-виджетов и вставка их в
пустые слоты `.ui`; подключение сигналов в `__init__` или `_wire()`; всё состояние
и данные.

**Загрузка `.ui` в библиотеке:** путь всегда рядом с модулем —
`os.path.join(os.path.dirname(os.path.abspath(__file__)), "<name>.ui")` (лежит в той
же папке-пакете), грузим `uic.loadUi(_UI_FILE, self)` (PyQt6). Promoted-`<header>` в
`.ui` — **полный** путь модуля с учётом папки:
`dark_pro_widgets.widgets.composite.<name>.<name>` (напр.
`...composite.connection_bar.connection_bar`). Promotion-адаптеры (тонкие подклассы
с конструктором `(parent)`, чтобы загрузчик `.ui` мог их инстанцировать) — вверху
composite-`.py` (см. `connection_bar._TransportSwitch`).

## 2. Оформление — только через `theme`, двумя разными путями

Цвета и шрифты берём **только** из `dark_pro_widgets.theme`: `BG`, `PANEL_BG`,
`FIELD_BG`, `BORDER`, `ACCENT`, `OK`/`WARN`/`ERR`, `TEXT`/`TEXT_DIM`, семантические
`PIPS`/`SIPM`, `FONT_FAMILY`/`MONO_FAMILY`, плюс `theme.rgba(hex, alpha)`. Хардкод
`#rrggbb` запрещён. `theme`/`qss` лежат в `core/`, но реэкспортятся плоско:
`from dark_pro_widgets import theme, qss`.

**Не путать два пути стилизации:**

1. **Стоковые Qt-виджеты** покрыты единым глобальным листом
   `qss.build_stylesheet()` (применяется один раз на уровне приложения). Варианты
   там — через **динамические свойства**: обычный `QPushButton` становится
   accent/danger так:
   ```python
   btn.setProperty("accent", True)
   btn.style().unpolish(btn); btn.style().polish(btn)
   ```
   Глобальный QSS ловит `QPushButton[accent="true"]` / `[danger="true"]`.

2. **Собственные виджеты dark_pro_widgets** ставят **свой** per-widget stylesheet и
   дают более богатый API вместо свойств — напр. `PrimaryButton(variant=...)` /
   `setVariant("accent"|"success"|"danger"|"neutral")` из таблицы `_VARIANTS`. Для
   нового кастомного виджета держим метод `_apply_style()`/`_apply_theme()`, который
   пересобирает лист из токенов темы, и зовём его при каждой смене состояния.

**Data-зависимое оформление**, которое нельзя выразить глобально (цвет точки
канала, фон области графика, бейджи), — в метод `_apply_theme()` в `.py`, красим
токенами темы. **Анимации** — через `QPropertyAnimation(self, b"<prop>")` над
`pyqtProperty` с `QEasingCurve` (см. анимацию `offset` в `toggle_switch`); простая
отложенная работа — `QTimer.singleShot`.

## 3. Библиотека презентационная — без бэкенда, с точками расширения

**Здесь НЕТ бэкенда** (ни Modbus/HDF5, ни async Event-шины — это живёт в
приложении-потребителе). Поэтому, добавляя поведение виджету, не пиши реальную
логику данных, а:

- оформляй его как **переопределяемые хук-методы и сигналы**, которые подключает
  downstream-проект — потребитель наследует виджет или переопределяет хук, чтобы
  вставить настоящую логику (duck-typing / override в Python). Дефолтная реализация
  = no-op, анимация или демо-поведение, поверх которого потребитель строит своё.
- клади **`demo_*`-хелпер** с фейковыми данными для превью (образец —
  `file_tree.demo_items()`), используемый только в блоке превью, не в проде.

### Запуск виджета в одиночку — абсолютные импорты, БЕЗ бутстрапа

**Никакого `runpy`/`sys.path`-костыля в начале файла.** Виджет должен запускаться
кнопкой Run в IDE как есть. Механика:

- **Виджет-модули используют абсолютные импорты** от корня пакета:
  `from dark_pro_widgets.core import theme` / `... import qss`;
  `from dark_pro_widgets.widgets.controls.slider import Slider`. Относительных
  импортов (`from . / .. / ...`) в запускаемых модулях быть не должно (в `__init__.py`,
  которые напрямую не запускают, относительные допустимы).
- **Пакет установлен editable** (`uv sync`, либо `uv pip install -e .`) — поэтому
  `import dark_pro_widgets` резолвится прямо в рабочее дерево. Именно это позволяет
  `python <файл>.py` найти пакет без всякого guard. Требование одно: интерпретатор
  IDE — это venv проекта с editable-установкой.
- **Запуск**: кнопка Run по файлу, либо `python -m dark_pro_widgets.widgets.<...>.<name>`,
  либо `uv run python <путь>`.
- Нижний `if __name__ == "__main__":` делает `from dark_pro_widgets.core._preview import preview`
  и `preview(build, title=...)`, где `build()` строит виджет(ы) **после** применения
  темы/QSS (QApplication должен существовать раньше любого QWidget). Для composite с
  `.ui` (напр. `connection_bar`) блок может собирать хост-окно и грузить `.ui` сам.

**Логи:** библиотека использует **loguru** (`from loguru import logger`), а не
стандартный `logging` — вопреки строчке в памятке приложения. Косметика (напр.
`theme.tint_window_board`) не должна ронять приложение: оборачиваем в try/except и
`logger.debug(...)`, продолжаем.

## 6. Разделение классов на модули

#### Когда разделять классы по разным файлам
Большой объем кода: Если один класс содержит сотни строк и сложную логику.Независимость: Если классы решают разные задачи и не зависят друг от друга.Удобство чтения: Когда разделение помогает быстрее находить нужный код.

#### Когда объединять классы в одном файле
Вспомогательные классы: Если маленький класс нужен только для работы основного главного класса.Логическая связь: Группа тесно связанных мелких классов (например, исключения для модуля или мини-модели).

## 11. Виджет — сборка из готовых примитивов («конструктор»)

Библиотека — это **набор переиспользуемых кирпичиков**, а виджет собирается из них.
Цель: каждый новый виджет пишется как можно проще — композицией уже готовых
элементов, а не вёрсткой с нуля.

**Порядок работы над виджетом:**
1. Прежде чем верстать руками — проверь, нет ли готового элемента в `controls` /
   `indicators` / `composite` (см. чек-лист «не дублируем»). Есть — переиспользуй.
2. Нужного элемента нет, но он имеет самостоятельный смысл (кнопка, бейдж, строка
   списка, поле, бар) — **вынеси его в отдельный переиспользуемый элемент** в нужный
   слой (`controls` — ввод/кнопки, `indicators` — отображение, `composite` — сборки),
   дай ему свой API + `_apply_theme()` + `demo_*`/превью, и **используй** в виджете.
   Не хорони переиспользуемый виджет приватным `_Class` внутри одного composite.
3. Только после этого собирай сам виджет — он должен читаться как список «взять то,
   взять это, связать сигналами», а не как сотни строк рисования.

**Что выносить, что оставлять приватным** (уточняет §6):
- **Выносить** — если у класса есть самостоятельная идентичность и он мог бы
  пригодиться в другом виджете: иконочная кнопка, цветной тип-чип, строка списка
  (лид-виджет + заголовок + подзаголовок), прокручиваемый список с выбором и
  клавиатурой, бар навигации с редактируемым путём. Хелперы-форматтеры
  (размер в байтах, склонения) — в `core`.
- **Оставлять приватным** — тонкий glue, завязанный на внутренности именно этого
  виджета: promotion-адаптеры для `.ui`, одноразовые лямбды, мини-модель записи.

**Признак кандидата на вынос:** приватный `_Foo(QWidget/QPushButton)`, который сам
рисует/стилизует законченную штуку (кнопка/бейдж/строка/список/поле). Если таких в
одном файле несколько — часть из них почти наверняка библиотечные примитивы, а не
приватные классы.

> Пример для разбора: `file_tree.py` держит `_ToolButton` (иконочная кнопка),
> `_Badge` (тип-чип), `_Row` (строка списка) и встроенный список с выбором — всё это
> кандидаты в переиспользуемые элементы (`controls`/`indicators` + примитив
> «список»). После выноса сам `FileTree` — тонкая сборка: бар-путь + список строк
> из `FileItem`.

## 12. API-шапка в докстринге модуля/класса

В начале **каждого** файла-виджета/модуля (докстринг модуля; для многоклассовых —
ещё и докстринг класса) — краткая **сводка API**, чтобы понять компонент, открыв
только шапку, не читая тело. Что включить:

- публичный класс(ы) и **сигнатуру конструктора** с аргументами;
- публичные методы — `имя(аргументы) → что возвращает`, одной строкой;
- **сигналы** — `имя(тип)`, когда испускаются;
- при необходимости — короткую строку «что это / зачем».

Одна строка на пункт; указывай аргументы и возвращаемое, когда неочевидно. Эталон
формата — `controls/icon_button.py` (блок «Публичный API:»).

Пример:

```py
"""PathBar — бар навигации: [‹ назад] [› вперёд] [редактируемое поле пути].

API:
* ``PathBar(parent=None)`` — собирает бар из двух IconButton и QLineEdit.
* ``set_path(text)`` — показать путь (курсор в конец → виден хвост).
* ``path() -> str`` — текущий текст поля.
* ``set_can_go_back(bool)`` / ``set_can_go_forward(bool)`` — доступность стрелок.
Сигналы: ``backClicked()`` · ``forwardClicked()`` · ``pathSubmitted(str)`` — по Enter.
"""
```

## 13. Оформление докстрингов классов и методов — Google style (PEP 257)

Базовый стандарт — **PEP 257**; конкретный формат секций — **Google style** (один
стиль на весь проект, не смешивать с NumPy/reST). Google выбран как самый
распространённый, читаемый и совместимый со Sphinx (Napoleon).

**Механика (PEP 257):**

- всегда `"""тройные двойные кавычки"""`;
- первая строка — краткое summary **одной** физической строкой, с точкой на конце;
  для класса она описывает, *что представляет экземпляр* («Кнопка…», «Бар навигации…»);
- многострочный докстринг: summary → **пустая строка** → подробности;
- после докстринга класса — пустая строка перед первым методом.

**Секции (Google): заголовок с двоеточием, тело с отступом 2–4 пробела.**

- **Класс:** `Attributes:` — публичные атрибуты (`имя (тип): описание`); для
  Qt-виджетов — `Signals:` (`имя(тип): когда испускается`). Аргументы конструктора —
  секция `Args:` в докстринге `__init__` (или в докстринге класса).
- **Метод/функция:** `Args:` (каждый параметр), `Returns:` (или `Yields:` для
  генераторов), `Raises:` (исключения). Секции **опускаем**, если имя + сигнатура
  самоочевидны — тогда достаточно одной строки-summary.

**Пример (класс + метод, Qt):**

```py
class PathBar(QWidget):
    """Бар навигации по каталогам: back/forward + редактируемое поле пути.

    Презентационный виджет: валидацию пути и историю ведёт владелец.

    Signals:
        backClicked(): нажата «назад».
        forwardClicked(): нажата «вперёд».
        pathSubmitted(str): путь из поля по Enter (без проверки).
    """

    def set_path(self, text):
        """Показать путь в поле.

        Args:
            text: строка пути; курсор ставится в конец, чтобы был виден хвост.
        """
```

**Связь с §12:** компактная «API:»-шапка в начале файла — быстрый индекс всего
модуля (сжатый Google без секций, «открыл заголовок — понял API»); докстринги самих
классов и методов — полный Google-стиль по правилам выше.
Пример:

``` py

переключателем и одним полем изменения параметра.

Инициализация:
* ``CtrlPanel(quantity_tile: int = 0)`` — Стоковый виджет, quantity_tile - количество плиток с телеметрией.

``set_title_widget(name: str, color: str)`` — задать название виджета и цвет метки.
```

## 14. Коммит после каждого завершённого изменения

После каждой завершённой правки (новый виджет/примитив, фикс, рефактор, правка
конвенций) — **сразу коммит** с понятным сообщением. Одна логическая правка = один
коммит; не копим кучу разнородных изменений в рабочем дереве.

- **Язык сообщений — английский** (единообразно, и заголовок, и тело).
- Тип по Conventional Commits: `feat` / `fix` / `refactor` / `docs` / `style` /
  `test` / `chore`, далее краткая суть — напр. `fix: remove file_tree border`.
- Перед коммитом — гейт: пакет компилируется (`compileall`), правка проверена
  (превью/рендер, где применимо).
- Коммитим на текущей ветке; **не пушим** без явной просьбы.

## 15. Виджет настраивается через API (стиль — фиксированный)

Разделяй в виджете **фиксированное** (стиль, оформление, поведение, структура-паттерн)
и **переменное** (тексты, лейблы, количество элементов, начальные значения, подписи
кнопок, набор опций). Переменное настраивается через API; фиксированное живёт внутри
(`_apply_theme`) и в API не выносится.

- **Повторяющуюся структуру задаём данными, а не хардкодом:** не «жёстко N элементов»,
  а список — сколько передали, столько построится в цикле.
- Стиль в параметры **не** выносим — он остаётся таким, как задуман.
- Даём геттеры значений и сигналы для взаимодействия.
- Так виджет становится настраиваемым переиспользуемым блоком (связка с §11).

**Как передавать — конструктор vs методы:**

- Скаляры/простые опции (флаг, размер, одиночная подпись) — можно параметром
  конструктора с умолчанием.
- **Наполнение (списки, коллекции, элементы) — методами** (`set_*` / `add_*`): создаём
  пустой экземпляр и настраиваем, а не пихаем список в конструктор. Так конструктор не
  разбухает, наполнение — инкрементально и по Qt-идиоме (`addItems` / `setCurrentRow`).
- Простой список — одним методом (`set_items(list)`); сложную/поэлементную структуру —
  `add_item(...) -> item` (метод возвращает элемент для прямой донастройки: иконка,
  данные, вложенные виджеты). «Список, где уместно; прямой доступ, где сложнее».

Предпочтительный вызов (образец — `controls/nav_list.py`):

``` py
nav = NavList()                                      # пустой экземпляр
nav.set_items(["Раздел A", "Раздел B", "Раздел C"])  # простой список — одним методом
item = nav.add_item("Раздел D")                      # сложнее — метод вернёт item
nav.set_current(0)
```

## 17. Короткий `__init__` — раскладку собираем вспомогательными методами

`__init__` должен читаться как **оглавление**, а не как вёрстка. Держи его коротким:
инициализация состояния → корневой layout → делегирование сборки зон в
`_build_*`-методы → `_apply_theme()`. Саму раскладку (создание виджетов, вложенные
layout'ы, margins/spacing) выноси в **вспомогательные методы**, по одному на
логическую зону.

**Правила:**

- **Зона = метод `_build_<зона>() -> QWidget`** (или `QLayout`): собирает свою часть
  и возвращает готовый контейнер. Внутри — создаёт виджеты, кладёт их в свой layout,
  сохраняет нужные ссылки в `self.*`, вешает локальные обработчики.
- **`__init__` не верстает руками** — только `outer.addWidget(self._build_header())`
  и т.п. По телу init сразу видно структуру виджета (шапка · плитки · подвал).
- Повторяющиеся куски (разделитель, строка «лейбл … поле») — свой мелкий
  хелпер-фабрика (`_hline()`, `_row(...)`), а не копипаст.
- Подключение сигналов — в `_wire()` или в том `_build_*`, что создал виджет;
  оформление — в `_apply_theme()` (§2). Эти три вида работы не смешиваем в init.

**Эталон — `composite/control_power_panel/control_panel.py`:**

``` py
def __init__(self, quantity_tile: int = 0, parent=None) -> None:
    super().__init__(parent)
    self.setObjectName("PowerCtrlPanel")
    self._tiles, self._seps = [], []

    outer = QVBoxLayout(self)
    outer.setContentsMargins(0, 0, 0, 0)
    outer.setSpacing(0)
    outer.addWidget(self._build_header())    # точка · название · питание
    outer.addWidget(self._hline())
    outer.addWidget(self._build_tiles())     # ряд плиток телеметрии
    outer.addWidget(self._hline())
    outer.addWidget(self._build_footer())    # подпись уставки · поле

    for _ in range(max(0, int(quantity_tile))):
        self.add_tile()
    self._apply_theme()

def _build_header(self) -> QWidget:
    """Шапка: точка состояния + название … переключатель питания."""
    ...
    return header
```

Связка: §1 (для `.ui`-виджетов init = `loadUi` + `_build_*`/`_wire`), §2
(`_apply_theme`), §11 (виджет — сборка из готовых примитивов).

## Чек-лист перед коммитом виджета

- [ ] Если есть `.ui` — пара `<name>.ui` + `<name>.py`, имена совпадают.
- [ ] В `.ui` нет логики и нет хардкод-цветов/шрифтов в `styleSheet`.
- [ ] Все виджеты из `.ui`, к которым обращается `.py`, аннотированы на уровне класса.
- [ ] Рантайм-виджеты кладутся в пустые layout-слоты, а не мимо layout.
- [ ] Цвета/шрифты — из `theme`; варианты стоковых кнопок — через свойства,
      кастомных — через `setVariant`/конструктор.
- [ ] Проверено, нет ли готового компонента в `dark_pro_widgets` (не дублируем).
- [ ] Виджет собран из готовых примитивов; недостающий переиспользуемый элемент
      вынесен в свой слой (`controls`/`indicators`/`composite`/`core`), а не оставлен
      приватным `_Class` внутри одного виджета (§11).
- [ ] Поведение — за переопределяемым хуком/сигналом, не хардкод-логика.
- [ ] Импорты абсолютные (`from dark_pro_widgets...`), в начале файла НЕТ
      `runpy`/`sys.path`-костыля.
- [ ] Есть `demo_*` и рабочий блок превью (`if __name__ == "__main__"`), файл
      запускается кнопкой Run напрямую (venv с editable-установкой).
- [ ] Объявление имен перед инициализацией
- [ ] Изменение закоммичено сразу после завершения (§14).
- [ ] Переменная часть — через API (наполнение/списки — методами `set_*`/`add_*`, а не
      конструктором); повторяющаяся структура из данных; стиль не параметризуется (§15).
- [ ] В шапке файла/класса — краткая сводка API (конструктор, публичные методы:
      аргументы → возврат, сигналы), чтобы понять компонент из заголовка (§12).
- [ ] Докстринги классов/методов — Google style (PEP 257): summary с точкой,
      пустая строка, секции `Args`/`Returns`/`Raises`/`Attributes`/`Signals` (§13).
- [ ] `__init__` короткий — читается как оглавление; раскладка вынесена в
      `_build_*`-методы по зонам, сигналы — в `_wire()`/`_build_*`, стиль — в
      `_apply_theme()` (§17).
